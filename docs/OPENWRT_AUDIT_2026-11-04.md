# Проверка OpenWrt на HEAD 288254f

Дата: 4 ноября 2026. Локальный HEAD и HEAD публичного репозитория совпадали:
`288254f94cead4bdf0d54d7322f7c609a362cbb6`. Изменения внесены в рабочее дерево.
Роутер, пользовательские настройки, опубликованные пакеты и теги не изменялись.
Зависимости, версии приложения и ядра не обновлялись.

Старый профиль с неправильным failover DNS исправляется только в RAM через
prepare.uc. Пользовательский DNS и DNS-группы сохраняют приоритет. Частный DNS,
явно выбранный пользователем, должен быть доступен через все выбранные туннели:
автоматически заменить такое пользовательское решение нельзя.

Окно 200 мс — ограничение арбитража отрицательных ответов, не задержка каждого
запроса. Положительный ответ возвращается немедленно. Если все участники уже
ответили, отрицательный ответ не ждёт это окно. Если один участник молчит,
реальный NXDOMAIN не ждёт общего четырёхсекундного timeout. Лимит остаётся
64 exchange и 2–4 участника. Отрицательный DNS-ответ не превращается в ошибку
транспорта. При полном транспортном отказе native pool возвращает ошибку;
внешний UDP hijacker sing-box может не отправить пакет клиенту. ucode helper
в такой ситуации сам возвращает SERVFAIL. Оба случая ограничены по времени.

## Сохранённые правила и ограничения политики

- auto_redirect, route_address_set, FakeIP, nftables, NFQUEUE и TUN сохранены.
  Не появился общий путь всего LAN через NFQUEUE.
- Доменные и rule-set маршруты до и после sniff сохранены. До sniff доступен
  восстановленный FakeIP-домен, после — имя из HTTP/TLS клиента с собственным
  DNS. Remote SRS/JSON нельзя считать навсегда исключительно IP-списками.
- DNS hijack остаётся до маршрутов; раннее private direct сохраняет приоритет
  перед явными CIDR. WG resolve перед ранним доменным маршрутом сохранён.
- Фиктивный параметр kernelDirect удалён из теста: вместо него действительно
  проверяются IPv4/IPv6 и remote SRS/JSON.
- Выбранный FakeIP и выбранные IP идут через TUN; обычные TCP/UDP остаются
  в Linux с первого пакета. В тесте проверяются реальные счётчики NFQUEUE.
- Внешний DNS по TCP/UDP 53 проходит прежний перехват. Собственный DoH/DoT,
  IP из стороннего DNS-кэша и прямое использование невыбранных IP не дают
  гарантии маршрутизации по доменному списку. Глобальный DNS-перехват и kill
  switch не добавлялись.
- При отключённой обработке IPv6 выбранные домены через DNS роутера не получают
  AAAA. Обычный IPv6 остаётся прямым. Это не глобальная блокировка IPv6 клиента.
- Пока служба работает, отказ туннеля не включает direct fallback для выбранного
  DNS. Полная остановка/авария всей службы не равнозначна kill switch:
  выбранные реальные CIDR могут снова стать прямыми до восстановления службы.

## Остаточные риски и физический роутер

1. Опубликованные ядра `.4` не заменялись. Изменения native DNS pool требуют
   пересборки ядра из этих исходников и отдельного процесса выпуска. Наличие
   прежнего номера `.4` само по себе не доказывает наличие новых Go-исправлений.
2. chroot использует настоящие ash/UCI/ucode и пакетные менеджеры. Доставка
   фоновой команды procd заменена транспортной фикстурой. Сам procd как init/PID 1,
   фактический OOM-killer и поведение watchdog физического устройства не проверены.
   SIGKILL worker и живые потомки проверены непосредственно.
3. Файловая блокировка DNS использует существующий
   [flock ucode](https://ucode-lang.org/ucode/module-fs.file.html#lock)
   и согласуется с блокировками
   [libuci](https://lxr.openwrt.org/source/uci/file.c).
   Абсолютную сериализацию любых внешних `mv`/записей без общей блокировки
   гарантировать нельзя. В libuci также есть переход от закрытия исходного fd
   к rename; произвольные внешние писатели вне удерживаемого flock остаются
   ограничением. Проверки конфликтов/конкурентных UCI проходят, но не доказывают
   отсутствие всех возможных межпроцессных interleaving.
4. При SIGKILL всей службы невозможно выполнить EXIT-восстановление DNS в тот же
   момент. Требуется проверка фактического respawn procd и восстановления dnsmasq
   на устройстве. Нормальная остановка с ошибкой восстановления теперь отменяется.
5. У простаивающей группы с urltest interval 5 минут невозможно одновременно
   сохранить гарантированное обнаружение отказа за 30 секунд и убрать все
   дополнительные сетевые пробы. Сохраняется пользовательский interval urltest;
   ошибки реальных подключений обрабатывает сама группа. Гарантия обнаружения
   idle-отказа раньше следующего urltest не заявляется. У фиксированного сервера
   прежняя одиночная 30-секундная проверка сохранена.
6. Protocol 253 используется как локальная метка владельца только для redirect
   routes интерфейса obhod-tun. Перед удалением проверяются все маршруты таблицы
   и селекторы правила. В закреплённом netlink нет поля protocol у policy rule,
   поэтому правило само по себе не доказывает принадлежность. Пустые неизвестные
   таблицы и непомеченные random tables прежних ядер нельзя
   надёжно отличить от чужих: они намеренно не удаляются автоматически. На старом
   устройстве после прежнего SIGKILL нужно отдельно проверить оставшиеся policy
   rules. Конфликтующие записи в помеченной таблице вызывают ошибку вместо удаления.
7. Исполнение ARM64/MIPS, производительность на 128 МБ RAM, flash overlayfs и
   реальные VPN-handshake здесь не проверены. Совместимость платформ проверялась
   каталогом и настоящими пакетными менеджерами на x86_64 rootfs.
8. На физическом 24.10 и 25.12 проверить: install auto/.4 lite/full с отказом
   загрузки/места; смену WG/VLESS/SOCKS/HTTP в группе; длительный TCP/UDP при
   одинаковом сохранении (тот же PID и соединение); WAN reconnect и смену
   публичного IP; firewall reload; SIGKILL/OOM worker и ядра; сторонние UCI/LuCI
   изменения DHCP; router DNS, внешний TCP/UDP 53, DoH/DoT и IPv6 включён/выключен.

Никакие пункты физической проверки не засчитаны как успешно выполненные.
